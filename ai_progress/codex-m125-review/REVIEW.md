## P1-01：容量角色仍混用，結構化資料和可見敘事互相矛盾

**根因與最早失真位置：** `engineering.py:40` 的封閉欄位只有 `supply_continuous_current`；`chat.py:_extract_user_supplied()` 的提示讓名目與實際共用此鍵。`chat.py:252–253` 對實際容量仍強制給 `mode='replace'`，這是將「並存容量限制」誤編碼成「替換」的確定性入口。`engineering.py:146–154` 以文件10A當基準建立 proposed_change。不是模型抽錯數字才會發生。

即使第一輪抽取完全正確，三輪都保留以下結構：

```json
{"fact_key":"supply_continuous_current","origin":"proposed_change",
 "change_mode":"replace","baseline_value":"10","value":"8","unit":"A"}
```

`analyzer.py:298` 又將 `limit_current_a=8` 寫進 Facts 的「電源額定 8 A」。`chat.py:844–854` 的備援仍寫「電源額定8A」「相對新方案本身的額定8A」。第三輪上方雖稱「本輪未變更」，下方仍沿用錯誤額定語意。第一輪更直接寫「supply_continuous_current 由10A換成8A」。這些不依賴 LLM，亦會隨 result 存入 analyses。

**證據：** observations 的 `A-semantics`、`B-semantics`、`three-turn-C`、`D-True`。對應獨立語意測試均失敗。

**建議：** 在對話情境及工程結果中分開保存額定容量、實際可用容量及各自來源；實際容量補充應標為條件／限制，不是額定替換。保留文件基準，仍不得寫回正式 facts。讓 Facts、Evidence、numbers 與兩種回覆共用此語意。只改 fresh/standing 顯示分組不足，不必因此重寫整個決策引擎。

## P1-02：M7 接受數字正確但語意錯誤的回覆

**最小重現：** 第一輪建立10A名目、8A可用、11A馬達；修正輪給正確抽取8A及9A，mock 回覆：

> 電源額定由10A改為8A，馬達改用9A。

API 仍回傳原文，`reply_source=llm_phrased`，即使使用者明確說兩種容量不變。

**根因：** `chat.py:_trusted_numbers_by_dimension()`（521行）、`_reply_is_trustworthy()`（581行）主要檢查數字屬於可信維度集合，10、8、9皆存在，所以沒有拒絕錯誤欄位角色和前後關係。`fresh_change_keys` 沒有成為 M7 的語意驗證依據。

**建議：** 重用 M7，在確定性條件／變更紀錄上驗證欄位角色與轉換宣稱，對無證據的額定變更拒絕。不可關閉 M7，也不能靠提示詞代替驗證；P1-01 的備援本身亦須修正。

## P1-03：文件基準被當成上一輪方案；正確差值沒有可信來源

**重現：** 11A馬達方案後改9A。備援寫「motor_continuous_current 由8A（文件 DOC-MOTOR）換成9A」，沒有本輪 **11→9A** 比較，沒有下降 **2A／48W**。Evidence 的 baseline_value 仍是文件8A。

**根因：** `engineering.py:154` 的 baseline 永遠遞迴計算無 override 的文件基準；`chat.py:964` 僅記錄哪些 key 不同，未建立上一輪計算及差值。`chat.py:827` 仍從文件 baseline 產生本輪敘事；M7 數字集合亦沒有 delta。

**建議：** 區分 document baseline、previous scenario、current scenario。用先前與當前的有效情境確定性計算 delta，附上來源與方向，再提供給回覆和 M7。保留文件比較，但清楚標為文件基準，不能冒充上一輪。不應直接把2、48加入任意允許清單。

## P2-01：fresh_change_keys 比較原始字典，等值格式會產生假變更

先建立8A；下一輪重述「電源實際可用仍是8.0A」或「仍是8000mA」。結果仍為8A，但回覆重新出現「supply_continuous_current 由10A換成8.0A／8000mA」。

**根因：** `chat.py:964` 使用 `existing_supplied.get(k) != v`，比較字串、單位字面和整個字典，不是歸一化物理量。這是新 freshness 實作的驗收缺口。

**建議：** 按欄位維度、角色、操作模式比較正規化 Decimal 值；同一物理量不算新變更，`add` 與 `replace` 的意義仍要區別。

## P2-03：逐字第一輪條件未被完整用於情境

另以使用者指定第一輪「電源24V，名目額定10A，實際可用8A，馬達11A，輔助3A」完成三輪。成功 mock 抽到11A，但第一輪計算沿用文件馬達8A，得到 **11A／264W**，未提示馬達11A未套用；後兩輪為12A／288W。

## 額外函式風險：尚未證明正常 API 路徑可觸發

`test_accepted_restatement_without_mode_does_not_hide_applied_state` 直接呼叫 `_unclaimed_change_intents()`：accepted 有8A但無mode，current_state 有已生效8A/replace，仍回報未套用。原因是 `chat.py:289` 先採 truthy accepted，未再核對 current_state。

**限制：** 現行 extractor 通常會為同一個明確請求加上mode，因此本次未證明一般 API 能產生這種輸入組合。此項是防禦性函式契約失敗，列入16個失敗斷言，但不當成已確認的使用者流程缺陷或獨立部署阻擋理由。
